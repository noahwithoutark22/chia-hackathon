# AES-128 Benchmark — Testbench Contract (Stage 1 of 6)

This file is the single source of truth for the cocotb+pyuvm testbench
conventions. Every later stage (2..6) reads this file instead of
re-deriving conventions from the RTL.

Authoritative references (do NOT modify):
- RTL:            `benchmarks/aes_benchmark/aes128.sv`
- RTL info:       `generated/designs/aes_benchmark/rtl/rtl_info.json`
- Specification:  `benchmarks/aes_benchmark/aes_spec.md`
- Reference model:`benchmarks/aes_benchmark/aes_reference_model.py`
  (`encrypt_block(key, plaintext) -> ciphertext`, byte oriented)

---

## 1. Top module name

| Field | Value |
|---|---|
| Top module | `aes128` |
| RTL source file | `benchmarks/aes_benchmark/aes128.sv` |
| Parameters | none |
| Description | Transaction-level, iterative AES-128 single-block encryption core (10 rounds, 3-state FSM IDLE/ROUND_RUN/FINISH) |

Testbench style: **cocotb + pyuvm, implemented entirely in Python.**
There is no SystemVerilog UVM testbench and no SystemVerilog `interface`.
All pin access is done through the cocotb `dut` handle.

## 2. DUT pin map (as implemented)

| Pin | Direction | Width | Type | Access in testbench |
|---|---|---|---|---|
| `clk` | input | 1 | logic | `dut.clk` (structural, clock - NEVER a transaction field) |
| `rst_n` | input | 1 | logic | `dut.rst_n.value` (structural, reset - NEVER a transaction field) |
| `start` | input | 1 | logic | `dut.start.value = <int>` / `dut.start.value` |
| `key` | input | 128 | logic | `dut.key.value = <int>` / `dut.key.value` |
| `plaintext` | input | 128 | logic | `dut.plaintext.value = <int>` / `dut.plaintext.value` |
| `ciphertext` | output | 128 | logic | `dut.ciphertext.value` (read) |
| `busy` | output | 1 | logic | `dut.busy.value` (read) |
| `done` | output | 1 | logic | `dut.done.value` (read) |

Rules:
- Drive width-128 pins with plain Python `int` in `[0, 2**128 - 1]`.
- Drive width-1 pins with plain Python `int` `0` or `1`.
- Reads return the signal's `.value` (an `int` in cocotb).
- `dut.clk` is driven only by the clocking coroutine, never by a UVM component.

## 3. Clock and reset

| Item | Value |
|---|---|
| Clock signal | `clk` |
| Clock edge | positive (`posedge`) |
| Reset signal | `rst_n` |
| Reset polarity | active-LOW |
| Reset type | asynchronous (async assert, posedge-clocked deassert / async deassert) |
| Reset deassert/reset_value | `state_reg=0`, `round_key=0`, `round=0`, `ciphertext=0`, `busy=0`, `done=0`, `state=IDLE` |

Conventions:
- Clock is generated by the test's clock coroutine (e.g. 10 ns half-period),
  started with `cocotb.start_soon(Clock(dut.clk, ..., units="ns").start())`.
- Reset is applied and released by the test; `rst_n` is held LOW for a few
  clock cycles at the start of simulation, then driven HIGH.

## 4. Transaction / sequence_item

Module: `tb/transaction.py` — class `AES128Transaction`
(`pyuvm.uvm_sequence_item` subclass).

All fields are **plain Python attributes** (`int`). Clock and reset are
structural and are deliberately NOT transaction fields.

| Field | Direction (in TB) | Type | Default | DUT pin(s) it maps to | Notes |
|---|---|---|---|---|---|
| `start` | input | `int` (1-bit) | `0` | `dut.start` | pulse that launches encryption; accepted while idle only |
| `key` | input | `int` (128-bit) | `0` | `dut.key` | AES-128 key |
| `plaintext` | input | `int` (128-bit) | `0` | `dut.plaintext` | 128-bit plaintext block |
| `ciphertext` | output | `int` (128-bit) | `0` | `dut.ciphertext` | result, valid when `done` pulses |
| `busy` | output | `int` (1-bit) | `0` | `dut.busy` | high while transaction active |
| `done` | output | `int` (1-bit) | `0` | `dut.done` | one-clock completion pulse |

Helper methods: `set_inputs(start, key, plaintext)`,
`set_outputs(ciphertext, busy, done)`, `__eq__`, `__repr__`,
`convert2string()`.

### Functional timing contract (for stage 2+)

- Start is accepted on a `posedge clk` when `dut.busy == 0` and `start=1`.
- `busy` goes high on that edge and stays high through the transaction.
- Exactly **12 clock cycles** after start acceptance, `done` pulses HIGH for
  exactly one clock and `ciphertext` holds the valid result.
- Changes to `key`/`plaintext` after start acceptance are ignored by the DUT.

### Reference model mapping

- Oracle: `aes_reference_model.encrypt_block(key_bytes, plaintext_bytes) -> ciphertext_bytes`
- The scoreboard must convert transaction `int` fields to 16-byte big-endian
  bytes before calling it and convert the returned bytes back to an `int`
  for comparison with `dut.ciphertext.value`.
- Output latency: **12 cycles** (registered output) — scoreboard must wait
  for `done`/latency before comparing `ciphertext`.

## 5. ConfigDB keys (shared objects)

pyuvm `ConfigDB` is the only sharing mechanism between components.
The keys below are canonical — do not invent alternatives.

| ConfigDB key | Type stored | Value | Used by |
|---|---|---|---|
| `"dut"` | `cocotb handle` (`SimHandleBase`) | the `dut` handle passed to the cocotb test | driver, monitor, helper, checker, test |
| `"dut_helper"` | `AES128DUTHelper` (from `tb/dut_helper.py`) | helper wrapping `"dut"` | driver, monitor, checker |
| `"clock_signal"` | `str` | `"clk"` | clock coroutine / test |
| `"reset_signal"` | `str` | `"rst_n"` | reset coroutine / test |

Conventions:
- `ConfigDB().set(None, "*", "dut", dut)` right after the cocotb test
  receives the `dut` handle.
- `ConfigDB().set(None, "*", "dut_helper", AES128DUTHelper(dut))`.
- Components read with `ConfigDB().get(self, "*", "dut")` /
  `ConfigDB().get(self, "*", "dut_helper")` etc.
- The `AES128DUTHelper` centralizes direct pin access
  (`helper.start.value`, drives `dut.start.value`, reads `dut.busy.value`, …)
  and is passed to `make_dut_helper(dut)` in `tb/dut_helper.py`.

## 6. Verification approach (for later stages)

- **Stimulus**: pyuvm sequences (`uvm_sequence`) on a `uvm_sequencer`;
  the driver converts `AES128Transaction` input fields into pin drives and
  samples the transaction into component pipelines.
- **Checking**: a Python reference-model scoreboard (authoritative oracle is
  `encrypt_block`), plus always-running plain-Python checker coroutines
  started with `cocotb.start_soon` that `assert` DUT behavior (replaces SVA).
- **Coverage**: `cocotb-coverage` (`CoverPoint` / `CoverCross`) sampled on
  the shared `coverage_db` (no SV covergroups).
- **Watchdog**: a deterministic watchdog / `with_timeout` wrapper bounded in
  clock cycles, in the test -- a hung test must fail, not exhaust the
  simulation. Verilator build uses `UVM_NO_DPI`.
- A generation manifest identifies the exact top module/compile order/test
  class names (integration stage).

## 7. Stage-3 observation additions (monitor + agent)

Appended by the observation stage; does **not** alter any earlier binding
field, pin, or key. Top module (`aes128`), §2 pins, §4 transaction fields,
and §5 ConfigDB keys are unchanged; the RTL and `rtl_info.json` remain
authoritative for implemented DUT structure.

### 7.1 `tb/monitor.py` — `AES128Monitor` (`uvm_monitor`)

- `build_phase` fetches `"dut"` and `"dut_helper"` (section 5 keys) and
  creates its own `uvm_analysis_port` named `"analysis_port"` (attribute
  `self.analysis_port`).
- Reconstructs each completed transaction entirely from the DUT pins
  through the shared `AES128DUTHelper` (observation-only; never drives):
  - **Stimulus** (`start`, `key`, `plaintext`) is captured at the moment
    the DUT accepts a request: `start == 1` while the DUT is idle
    (`busy == 0` in the preceding cycle). Acceptance probes, in order:
    the mid-cycle falling-edge probe (`start==1`, `busy==0`, `rst_n==1`),
    the latching rising-edge probe (`start==1` with `prev_busy==0`; the
    DUT asserts `busy` on the same edge that latches `key`/`plaintext`),
    and a busy-rise fallback that publishes only when the captured
    `start` is still 1 (so the "start while busy" poke is never mistaken
    for an acceptance).
  - **Outputs** (`ciphertext`, `busy`, `done`) are sampled on the rising
    edge where `dut.done == 1` with post-edge values: `ciphertext` holds
    the valid result, `busy` is 0 (deasserted on the same edge), `done`
    is 1 — exactly the §4 "valid when `done` pulses" rule.
- Publication: one `AES128Transaction` per completed transaction, all six
  §4 fields filled, written via `analysis_port.write(item)`.
  `published_count` / `dropped_count` counters are exposed for the env
  report.
- Observation-only: the monitor never drives pins and never fails the
  test by itself. A transaction is **dropped** (no item published) when
  an asynchronous reset aborts it (`rst_n == 0`), when `busy` falls
  without `done`, or when no `done` arrives within `done_timeout_cycles`
  (default 1000, well above the 12-cycle latency; the last case is logged
  as an error, but the always-running watchdog from §6 / the integration
  stage is the mechanism that fails a genuinely hung test). Later stages
  must therefore **not** assume a 1:1 monitor-item ↔ sequence-item
  pairing when reset injection is enabled.
- Sampling is synchronized on `RisingEdge(dut.clk)` (and mid-cycle
  `FallingEdge` probes), reading post-edge values directly — the
  canonical cocotb replacement for a SystemVerilog clocking-block
  monitor. No `ReadOnly()` wait is used: stimulus capture at the latching
  edge must read the offer *before* the driver's same-edge release.

### 7.2 `tb/agent.py` — `AES128Agent` (`uvm_agent`)

- Encapsulates the stage-2 `AES128Driver` / `AES128Sequencer` and the
  stage-3 `AES128Monitor`. Exposes attributes `driver`, `sequencer`,
  `monitor` (children named `"driver"`, `"sequencer"`, `"monitor"`) and
  one `uvm_analysis_port` named `"analysis_port"`.
- `build_phase` calls `super().build_phase()` (pyuvm sets
  `is_active = UVM_ACTIVE`, overridable via ConfigDB key `"is_active"`),
  then creates `analysis_port` + `monitor`, and — only in active mode —
  `driver` + `sequencer`. If the stage-2 modules are absent, building an
  *active* agent raises a clear `RuntimeError` (a passive, monitor-only
  agent does not need them).
- `connect_phase`: in active mode
  `driver.seq_item_port.connect(sequencer.seq_item_export)`; in both
  modes `monitor.analysis_port.connect(agent.analysis_port)`.
- The environment (integration stage) builds this agent and starts
  sequences on `agent.sequencer`.

### 7.3 ConfigDB retrieval-path clarification (pyuvm 5.0, no contract change)

The §5 keys (`"dut"`, `"dut_helper"`, `"clock_signal"`,
`"reset_signal"`) and their stored values are unchanged. Stage-3+
components retrieve them as `ConfigDB().get(self, "", <key>)` (and
`ConfigDB().get(None, "", <key>)`) rather than with a literal `"*"`
retrieval path: pyuvm 5.0 — the pinned runtime for this bench (the
simulation worker installs `cocotb==2.1.0`, latest `pyuvm` ≡ 5.0,
`cocotb-coverage`) — accepts `"*"` as a **store** scope
(`set(None, "*", key, value)`) but rejects wildcard **retrieval** paths
in `ConfigDB.get`. The empty path resolves to the caller's scope and
`fnmatch(caller_path, "*")` matches the wildcard store; this is the same
resolution the i2c_master bench settled on. Store sites in the test top
keep the §5 form `ConfigDB().set(None, "*", key, value)`.

### 7.4 Latency note (RTL reading vs the §4 12-cycle claim)

A straight-line reading of the RTL FSM (IDLE latches on the acceptance
edge; 10 ROUND_RUN edges; the FINISH edge assigns `done <= 1`) places
the `done` pulse 11 rising edges after the acceptance edge (the 12th
cycle if the acceptance cycle itself is counted as cycle 1). This does
not affect the monitor, which latches onto the `done` pulse itself; the
scoreboard (stage 4) and the latency checker (stage 5) are advised to
key off the `done` pulse rather than a hard-coded cycle count.

### 7.5 Monitor abort/acceptance refinement (transition-based; no contract change)

Refinement of the §7.1 drop/acceptance wording only — no field, pin, key,
or protocol claim changes. Validation against the real RTL (Icarus +
cocotb 2.1.0 end-to-end smoke) showed that under some simulators the DUT
samples a driver's input write one posedge **later** than the edge the
write lands after, so the acceptance edge can be either the first or the
second posedge after the offer appears. The shipped monitor is therefore
strictly **transition-based** on `busy`:

- A transaction completes only when the `done` pulse is observed (never by
  a busy level).
- A transaction is dropped only on a real `busy` 1 -> 0 transition without
  `done` (mid-flight abort), on `rst_n == 0`, or on the
  `done_timeout_cycles` hang bound.
- While `busy` reads 0 and `start` is still 1 the monitor keeps waiting
  (the offer may still be accepted on the next edge); if `busy` reads 0
  and `start` is withdrawn (no acceptance edge ever occurred), the monitor
  re-arms the start wait without publishing and without moving
  `dropped_count` (`_NOT_ACCEPTED` sentinel).

## 8. Stage-4 scoreboard addition (scoring)

Appended by the scoring stage; does **not** alter any earlier binding
field, pin, or key. Top module (`aes128`), §2 pins, §4 transaction fields,
and §5 ConfigDB keys are unchanged.

### 8.1 `tb/scoreboard.py` — `AES128Scoreboard` (`uvm_scoreboard`)

- `build_phase` fetches `"dut"` / `"dut_helper"` (section 5 keys, §7.3
  retrieval form; diagnostic use only) and creates a
  `uvm_tlm_analysis_fifo` named `"aes128_analysis_fifo"`. The scoreboard
  exposes the fifo's TLM export as attribute `analysis_export`; the
  environment connects `agent.analysis_port.connect(scoreboard.analysis_export)`.
- Consumes exactly the §4 monitor items: one published
  `AES128Transaction` per completed, **non-reset-aborted** transaction.
  Reset-aborted / timed-out transactions were already dropped by the
  monitor (§7.1 / §7.5) and never reach the scoreboard.
- Oracle: `aes_reference_model.encrypt_block(key_bytes, plaintext_bytes)`
  (module `tb/aes_reference_model.py`, verbatim copy of
  `benchmarks/aes_benchmark/aes_reference_model.py`; fallback imports the
  authoritative `benchmarks/aes_benchmark` directory). The §4 `int` fields
  are converted to/from 16-byte big-endian blocks (MSB = AES state byte 0,
  matching the RTL byte mapping) before calling the oracle.
- Comparison happens at the `done` pulse implied by the item — no
  cycle-counting (per §7.4, key off the `done` pulse). DUT `ciphertext`
  is compared byte-by-byte against the oracle result; any single-byte
  mismatch counts as a failure and is reported with the transaction
  number, DUT ciphertext, expected ciphertext, key, and plaintext in hex.
- Counters exposed for the environment report: `transactions`, `matches`,
  `mismatches`, plus `results()` (dict summary) and a `passing` property.
  The scoreboard logs but does not raise on mismatch; the environment /
  test stage fails the run on a nonzero `mismatches` count.

### 8.2 `tb/aes_reference_model.py` — oracle copy

Verbatim copy of `benchmarks/aes_benchmark/aes_reference_model.py`
(byte-identical, produced with `cp`; not hand-written). If the copy is
missing, `tb/scoreboard.py` falls back to importing
`aes_reference_model` from the authoritative `benchmarks/aes_benchmark`
directory. Never modify either copy; the benchmark file remains
authoritative.
## 9. Stage-6 integration additions (assembled testbench)

Appended by the integration stage; does **not** alter any earlier binding
field, pin, key, monitor behavior, or scoring rule.

### 9.1 Component inventory (all Python, no generated SystemVerilog)

| File | Component | Role |
|------|-----------|------|
| `tb/driver.py` | `AES128Driver` (`uvm_driver`, active) | Pulls §4 items from the sequencer; offers them on `start`/`key`/`plaintext`; holds the offer until `busy` rises (bounded 16 cycles), a reset aborts it, or the bound expires; then releases `start` only (key/plaintext stay stable until the next offer, §7.5). | `tb/test.py` | `AESTestBase` + 13 concrete `uvm_test` classes | Pass/fail verdict: raises in `report_phase` on scoreboard `mismatches > 0`, or on `REQUIRES_TRANSACTIONS and transactions == 0`. |
| `tb/test_top.py` | `aes128_tb` (`@cocotb.test`) | Clock, bench reset, §5 ConfigDB keys, watchdog, `run_test(UVM_TESTNAME, keep_singletons=True)`. |

### 9.2 Test classes (`UVM_TESTNAME` values)

`AESNistKatTest`, `AESAllZerosTest`, `AESAllOnesTest`,
`AESAlternatingTest`, `AESZeroKeyNonzeroPtTest`,
`AESNonzeroKeyZeroPtTest`, `AESInputChangeWhileBusyTest`,
`AESRepeatedTransactionsTest`, `AESDonePulseWidthTest`,
`AESResetDuringIdleTest`, `AESResetMidTransactionTest`,
`AESCornerCaseTest`, `AESRandomizedTest`.

`AESResetMidTransactionTest` sets `REQUIRES_TRANSACTIONS = False` (the
plan's reset-abort scenario completes no transaction by design; its
post-reset pin checks live in `ResetMidTransactionSeq`).

### 9.3 Scenario orchestration

Directed tests start their `SEQUENCE_CLASS` on
`env.agent.sequencer` under a run-phase objection, then drain several
clock cycles so the scoreboard consumes the final monitor items before
`report_phase`. `AESCornerCaseTest` runs the five corner sequences
back-to-back; `AESRandomizedTest` reads `AES_NUM_RANDOM` (1000),
`AES_IN_FLIGHT_RESET_PROB` (0.05), `AES_IDLE_RESET_PROB` (0.10) and
`AES_SEED` (optional). Import-time guards
(`verify_directed_scenario_ids`, `verify_directed_test_scenario_ids`)
fail the run if the plan/sequence/test scenario-ID chain drifts.

### 9.4 DISC-001 flag (intended bug detection; do not "fix")

The target RTL `aes128.sv` is intentionally buggy per verification plan
`DISC-001`: the final-round MixColumns guard `if (round == 4'd10)`
never fires because `round` tops out at 9 during `ROUND_RUN`, so
MixColumns runs in all ten rounds. Verified against the exact RTL
algorithm: DUT ciphertext for the FIPS-197 vector is
`0xd961a18ca92dd978fb987b3ae7a8d9cd` whereas the reference model
produces `0x69c4e0d86a7b0430d8cdb78070b4c55a`.

Per "Verification isolation", the scoreboard compares against the
reference-model oracle — never against the RTL — so **every test that
completes at least one transaction fails on a scoreboard mismatch**.
That failure is the intended detection outcome. Only
`AESResetMidTransactionTest` is expected to pass. Sequence layers must
never assert expected ciphertext values; they only check structural
timing premises (single-cycle `done`, `done` accompanies `busy`
deassertion, reset clears outputs) that are scenario premises rather
than cryptography.

### 9.5 Environment defaults

`AES_CLK_PERIOD_NS=10`, `AES_WATCHDOG_CYCLES=500000` (generous bound;
counts rising clock edges, fails the run if exceeded; killed in
`test_top`'s `finally`). Randomized knobs as in §9.3.
