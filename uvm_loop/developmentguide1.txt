# CHIA LLM-UVM TB Generator — Rebuild & Development Guide

## 1. Goal

This project uses CHIA to orchestrate an automated RTL verification flow:

    CHIA
      |
      +-- RTL worker ------> Verible ------> rtl_info.json
      |
      +-- OpenCode worker --> LLM ---------> UVM testbench
      |
      +-- Verilator worker ----------------> simulation
                                                |
                                                +--> failures --> LLM repair

Design principle:
- CHIA/Ray: orchestration
- Verible: deterministic RTL structure extraction
- OpenCode + LLM: reasoning, UVM generation and repair
- Verilator: compilation/simulation
- Docker: isolated tool dependencies

## 5. Why Verible

The LLM should not infer basic RTL structure when a deterministic parser can provide it.

We considered Tree-sitter, Verilator, Slang and Verible. We selected Verible because the project wants a concise structural representation rather than a dense semantic AST.

Desired representation includes:
- module
- parameters
- ports
- directions
- widths
- relevant types

Example:

    {
      "module": "adder",
      "parameters": [
        {
          "name": "WIDTH",
          "default": {
            "kind": "number",
            "value": "8"
          }
        }
      ],
      "ports": [
        {
          "name": "a",
          "direction": "input",
          "width": {
            "left": {"kind": "identifier", "value": "WIDTH"},
            "right": {"kind": "number", "value": "0"}
          }
        }
      ]
    }

This is our concise representation derived from Verible, not the raw Verible syntax tree.

## 6. Verible Docker Worker

Verible is not required on the host. It is installed inside a CHIA-based Docker image.

`workers/rtl/Dockerfile`:

    FROM ghcr.io/ucb-bar/chia:latest

    USER root

    RUN apt-get update && \
        apt-get install -y --no-install-recommends \
            curl \
            ca-certificates \
            jq \
        && rm -rf /var/lib/apt/lists/*

    RUN LATEST_TAG=$(curl -fsSL https://api.github.com/repos/chipsalliance/verible/releases/latest | jq -r .tag_name) && \
        echo "Installing Verible ${LATEST_TAG}" && \
        curl -fsSL \
            "https://github.com/chipsalliance/verible/releases/download/${LATEST_TAG}/verible-${LATEST_TAG}-linux-static-x86_64.tar.gz" \
            -o /tmp/verible.tar.gz && \
        tar -xzf /tmp/verible.tar.gz -C /opt && \
        ln -s /opt/verible-${LATEST_TAG}-linux-static-x86_64/bin/* /usr/local/bin/ && \
        rm /tmp/verible.tar.gz

    USER ray
    WORKDIR /home/ray

Important:
- Do not use the old `entrypoint.py`.
- Do not add an ENTRYPOINT for the worker.
- CHIA manages worker/Ray startup.

## 7. Build the Verible Image

From the repository root:

    docker build -t chia-rtl-worker:local -f workers/rtl/Dockerfile .

Verify:

    docker run --rm \
      --entrypoint verible-verilog-syntax \
      chia-rtl-worker:local \
      --version

The build prepares the worker environment; it does not run Verible against RTL.

## 8. ORFS vs Verible Containerization

The existing ORFS worker mounts host-side source/build state, for example:

    -v ${CHIA_ORFS_REPO}/orfs-native-build:/root/OpenROAD-flow-scripts
    -v ${CHIA_ORFS_REPO}:/root/chia-orfs
    -e PYTHONPATH=/root/chia-orfs

That is intentional because ORFS uses live repository/build state.

Our Verible worker instead contains the Verible executable in the image. RTL is supplied at runtime.

So:

    ORFS:
    Docker environment + host repository/build state

    Verible:
    Docker environment + runtime RTL/workspace

## 9. Example RTL

`examples/adder/adder.sv`:

    module adder #(
        parameter WIDTH = 8
    ) (
        input  logic             clk,
        input  logic             rst_n,
        input  logic [WIDTH-1:0] a,
        input  logic [WIDTH-1:0] b,
        input  logic             cin,
        output logic [WIDTH-1:0] sum,
        output logic              cout
    );

      always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
          sum  <= '0;
          cout <= 1'b0;
        end else begin
          {cout, sum} <= a + b + cin;
        end
      end

    endmodule

## 10. Specification and Reference Model

The adder specification describes:
- registered WIDTH-bit addition
- carry-in/carry-out
- overflow
- reset
- randomized WIDTH=8 testing

The example intentionally contains a useful specification-vs-RTL inconsistency: the spec discusses synchronous/immediate reset behavior while the RTL uses `@(posedge clk or negedge rst_n)`. Keep this during testing so the LLM has to reason about the discrepancy.

The reference model is plain Python and is the golden functional model:

    def adder_ref(a: int, b: int, cin: int, width: int = 8) -> tuple[int, int]:
        mask = (1 << width) - 1
        total = (a & mask) + (b & mask) + (cin & 1)
        sum_out = total & mask
        cout = (total >> width) & 1
        return sum_out, cout

Keep the reference model as the ground-truth functional model.

## 12. CHIA Cluster Architecture

The intended resources are:

    hello_rtl
        resources: {"rtl_extract": 1}

    hello_opencode
        resources: {"opencode_creds": 1}

    hello_verilator
        resources: {"verilator_run": 1}

This keeps the environments separate instead of creating one large worker containing Verible + LLM + Verilator.

## 13. Current cluster.yaml

Relevant configuration:

    provider:
        head_ip: ${THIS_MACHINE}

    auth:
        ssh_user: ${USER}
        # ssh_private_key: ~/.ssh/<ssh_key_name>

    available_node_types:

        hello_verilator:
            resources: {"verilator_run": 1}
            num_workers: 1
            compatible_ips: [${THIS_MACHINE}]

            docker:
                image: "ghcr.io/ucb-bar/chia-verilator-run:latest"
                container_name: "chia-verilator-${USER}"
                run_options:
                    - --ulimit nofile=65536:65536
                    - --shm-size=10.24gb

        hello_opencode:
            resources: {"opencode_creds": 1}
            num_workers: 1
            compatible_ips: [${THIS_MACHINE}]

            worker_setup_commands:
                - "source ~/.bashrc"

            docker:
                image: "ghcr.io/ucb-bar/chia-opencode:latest"
                container_name: "chia-opencode-${USER}"
                run_options:
                    - -v ${HOME}/.local/share/opencode/auth.json:/home/ray/.local/share/opencode/auth.json:ro

        hello_rtl:
            resources: {"rtl_extract": 1}
            num_workers: 1
            compatible_ips: [${THIS_MACHINE}]

            docker:
                image: "chia-rtl-worker:local"
                container_name: "chia-rtl-${USER}"
                pull_before_run: false
                run_options:
                    - --shm-size=2gb

    head_env_commands:
        - "source ~/.bashrc && conda activate chia_env"

    head_setup_commands:
        - "source ~/.bashrc && conda activate chia_env"

    head_start_ray_commands:
        - "source ~/.bashrc && conda activate chia_env && ray stop"
        - "source ~/.bashrc && conda activate chia_env && \
            ray start --head --port=6379 \
            --include-dashboard=True --dashboard-agent-listen-port=0"

    worker_start_ray_commands:
        - "ray stop"
        - "ray start --address=$RAY_HEAD_IP:6379 --dashboard-agent-listen-port=0"

Important:
- Do not copy another developer's `${CHIA_ORFS_REPO}` paths into this cluster.
- The OpenCode worker currently only needs the auth.json mount.
- Replace `<ssh_key_name>` with a real key if required, or comment it out when using an SSH agent.

## 14. OpenCode

OpenCode is used through CHIA's existing OpenCode worker rather than a custom LLM Dockerfile.

OpenCode supports runtime model selection:

    opencode run -m <provider/model> "..."

A free model successfully tested during development:

    opencode/nemotron-3.5-lightning-free

The same worker can later use a paid model without changing the worker image.

Authentication is mounted from:

    ${HOME}/.local/share/opencode/auth.json

Do not commit auth.json.

## 15. Why We Are Not Building an LLM Dockerfile

CHIA already provides:

    ghcr.io/ucb-bar/chia-opencode:latest

and the `opencode_creds` resource.

Therefore the project should reuse CHIA's OpenCode worker.

Our custom Docker image is for Verible because Verible is an external RTL-analysis dependency that we want isolated and reproducible.

## 17. Rebuild Checklist

1. Install Docker:

       docker --version

2. Install/activate CHIA:

       conda activate chia_env

3. Verify CHIA:

       python -c "from chia.base.ChiaFunction import ChiaFunction; print(ChiaFunction)"

4. Clone/copy the repository:

       git clone <repo>
       cd llm-uvm-tb-generator

5. Set machine address:

       export THIS_MACHINE=$(hostname -I | awk '{print $1}')

6. Verify OpenCode auth:

       ls -l ~/.local/share/opencode/auth.json

7. Build Verible worker:

       docker build -t chia-rtl-worker:local -f workers/rtl/Dockerfile .

8. Verify Verible:

       docker run --rm --entrypoint verible-verilog-syntax chia-rtl-worker:local --version

9. Start/add the CHIA cluster according to the CHIA deployment setup.

10. Check resources:

       ray status

    and:

       python -c "import ray; ray.init(address='auto'); print(ray.cluster_resources())"

    Look for:
       rtl_extract
       opencode_creds
       verilator_run

11. Run RTL extraction:

       python -m pipeline.test_extract

12. Inspect:

       cat generated/rtl/rtl_info.json

## 18. Historical Debugging Notes

### Ray remote-function mistake

This was wrong:

    ray.get(f)

because `f` is a RemoteFunction.

Correct:

    ray.get(f.remote())

### Running OpenCode from the wrong directory

OpenCode can write files in its active project/workspace. For project work:

    cd /path/to/workspace
    opencode run ...

### Old RTL worker entrypoint

The initial worker used `entrypoint.py` and manually launched Docker. That was useful for proving Verible worked but is not the final CHIA-native architecture.

Old concept:

    CHIA -> docker run -> entrypoint.py -> Verible

Final concept:

    CHIA -> Ray scheduler -> rtl_extract resource
         -> CHIA worker container -> extract_rtl() -> Verible

### Python package rename

The project package was renamed from `chia/` to `pipeline/` to avoid confusion with the installed CHIA package.

Current imports should therefore use:

    from pipeline.functions import extract_rtl

rather than:

    from chia.functions import extract_rtl
